# Spoken acts: how the voice says T3 news

Nothing the voice says about T3 work is a hard-coded string (Mason, 2026-11-18). When he asks how a thread is going, he hears a short answer drawn from the thread's records, not the first two sentences of its last reply.

## The path

1. Code emits a typed act with the facts and evidence sequences from a T3 result, event, or read. For example, `confirm_tell` carries the thread title and the proposed message.
2. A separate text-only LFM3 realtime session drafts a short line. It gets instructions for the act kind, including an example that treats a thread title as the name of an existing conversation. Set `VOICE_RENDERER=particle-1` for the OpenRouter text model, `VOICE_PAID_TEXT_MODEL` to opt into a paid text model, or `VOICE_RENDERER=local` for a separate local chat server. [Local renderer probe](local-renderer.md)
3. Code checks the draft's form and named values. It rejects known thread or project titles and titles from prompt examples unless the act supplies them. A confirmation must be a question, and a line about a pending need must describe the need without reading out a command, path, or code. Liquid d1.2 then answers yes-or-no questions about the act's meaning, status, and factual claims. Both checks must pass.
4. A private text item hands the draft to the call's existing audio session, which says it. The call receives instructions to say the item's words and nothing else when the session opens, with no announcement, lead-in or closing line of its own. Those instructions must be in place before the first audio turn, because the realtime server then locks them.
5. The live server holds the call's audio until the complete reply text is the draft's words: the same words, up to case, punctuation, markdown and contractions, with no person flip, so "I asked" is never "you asked". The draft already passed both checks, so the same words need no second decider call, and any other words are not the checked line. The turn stops the response at the first word that leaves the draft, so a reply that goes off the words leaves only its start in the session: llama.cpp keeps everything a response generated and has no event that removes an item (`server-realtime.cpp`: a cancel ends the response at the token it reached, and the dispatch accepts only session, audio-buffer, item-create, response-create and response-cancel events). What the build allows, then, is that the stopped start stays in the session, and the measured question is whether the next reply carries it on: in 12 forced cancels, none did (GPU). No note about the held reply is sent, because the one that told the model to set it aside was read as the newest text and answered. A reply that leaves the words is asked once more in the same turn with the same note (`MAX_RELAYS`). One that fails twice, has no audio, or is cut off goes back to be said when the call is quiet (`run_idle`), and a question goes back too, because nobody can answer a question they never heard. A question waits that way only while it is still the open one nobody has heard: once a turn asks it again, or a reply drops it, the waiting line is dropped with it (`T3Tasks.askable`). If the person starts talking while idle news is still being drafted, their turn can start without waiting for the draft. A confirmation that was never heard is asked again before a yes can authorize an action.

A yes authorizes one prompt. The question the voice asked belongs to the call it was asked in, and only a prompt whose audio was sent (`T3Tasks.spoke`) can be answered. The next person turn answers it or drops it: an unrelated reply, a turn that ends without answering, another line said after it, a hang-up, a reconnect and 90 s since it was heard (`CONFIRM_TTL_S`) all clear it, and a question is never asked a second time on the strength of a reply that answered nothing. A prompt the person never heard comes back to be asked again and acts on nothing. When a second prompt replaces the first, only the last one can be answered.

Picking the thread: the decider picks the thread a request means, and no chat model or word match does (`Decider.picks`, voice/t3/verify.py). One typed choice has the listed threads as its options, newest first and up to 40, each with its project and state, plus "not listed" (the words name or describe a thread that none of them is) and "unclear"; the thread the call last spoke about rides along, so "it" can mean that one. The answer's shares decide what happens. A thread with 0.9 or more is one the decider is sure of: a question about it is answered at once, with no "do you mean". A thread with 0.5 or more is confirmed back, unless the request is a question about the thread this call last spoke about: that one is answered at once, because an ask only reads and its answer names the thread. Otherwise the voice asks which, offering the threads that got 0.1 or more, or the three newest when none did. "Not listed" says there is no such thread. A message or a stop is always confirmed, however sure the pick. A question about a thread whose title another thread shares is confirmed too, and a message or a stop for such a title is not offered at all: the question could only name the title, so a yes could act on the wrong thread, and the voice says so (`same_title`). When the decider saw only part of the listing, "not listed" says how many threads were checked. No answer (no decider, a timeout) picks nothing and asks. On the recorded picks (`voice/t3/fixtures/thread_picks.json`, d1.2, 90 rows: 45 made-up requests over a listing of 12 and one of 40, 40 rows from requests written before any was run) 88 rows are placed as their case says, and no row is sure of a thread the request does not mean. The two misses are "and that one?" over each listing, which gives the thread last spoken about 0.50 (0.3 to 0.68 in earlier recordings); it is the only thread offered, so it is still confirmed. A pick is one decider call, a median of 121 ms and a p95 of 253 ms over the 90 recording calls (measured), off the T3 lock. The local d1-2B gives the thread it rightly picks a lower share than the hosted d1.2 does, so its client sets its own sure bar, 0.7 (`D1Client.pick_sure`), chosen on the same 90 rows: 70 are then placed as their case says, against 46 at 0.9, and no row is sure of a wrong thread (`voice/t3/fixtures/local_thread_picks.json`, measured). On the 40 rows of `voice/t3/eval/pick_holdout.py` the local d1-2B places 39 and the hosted d1.2 places 38, neither sure of a wrong thread (measured). Those 130 rows tuned the "not listed" wording: worded as "a thread that is not one of these", the local d1-2B called a vague "how is that one?" with nothing discussed not listed on 10 of its 16 such requests, and now on none; it seems to have read the option as "none of these" (inferred). On 32 more rows written before that and scored after (`voice/t3/eval/fresh_holdout.py`), the local d1-2B places 28 and d1.2 places 32, neither sure of a wrong thread and neither calling any of the 8 vague requests not listed (measured; an earlier wording was scored on them first, and the one change after was made for a regression d1.2 showed on the 130 rows). The local misses left are "it" with a thread just spoken about, which it mostly asks about rather than confirms, and descriptions by state ("the one that failed").

Reading the answer: the decider reads every reply to a T3 question (`Decider.reads`, voice/t3/verify.py), and no word list or pattern in code reads it. One typed question asks what the reply does: yes, no, a question, another target, or nothing. A yes acts only when it is unconditional: the label is yes with at least 0.5 of the weight, no real share (over 0.2) goes to a no, a question or another target, the last two together stay under 0.25, and no change of project is read beside it, so "yes, only after the tests pass" is never a yes. A no cancels. A question or an unrelated reply answers nothing and the question is dropped. When a launch question has other projects it could mean, the same call carries a second question: does the reply keep the proposed project, change to a named one, or change without making clear which. A named change, or a change with only one other project, asks a new confirmation for that project; a change with several asks which. A named project still goes through `pick_project` first. A question that lists choices ("which thread", "which project") sends the list in the order it was said and asks which one the reply chooses, so "the second one" answers by place and "the clamp one" by name. A reply to "which thread" that asks for a thread that was not listed is looked up among every thread, as a new reference; any other reply that chooses none drops the question, which is never asked twice. Threads that share a title cannot be told apart by voice, so the newest stands for the title, and one title left is confirmed, not listed. A reply the decider cannot read (no decider, a timeout, a score that is not a number from 0 to 1) answers nothing, so nothing acts. On the recorded replies (`voice/t3/fixtures/reply_reads.json`, d1.2, 102 rows) every yes reply acts and no other reply does, every plain no reads as no, and all but one of the replies with other projects or a list on offer are placed correctly. The miss is "yes, but in the other project", read as keeping the proposed project; it is still not a yes, so nothing starts. The local d1-2B acts on the same 29 yes replies and on no other (`voice/t3/fixtures/local_reply_reads.json`). It acted on 22 before the request said the transcript's punctuation is guessed and that a short agreement (okay, sure, mm-hmm, please do) counts as a yes: it read a rising "please do?" as a question and a bare "okay" as unrelated. On 41 replies written before that and scored once (`voice/t3/eval/fresh_holdout.py`), the local d1-2B acts on 17 of 18 yes and d1.2 on 15 of 18, and neither on any of the 23 others (measured). The misses are a yes that names the thread again ("yes, the timetable one"), which puts 0.21 to 0.45 on a changed target, and, on d1.2, a rising "yeah?"; each answers nothing. Each read is one decider call before anything happens, a median of 118 ms over the 102 calls of the last recording run (measured). The decider is a network call, so it is asked off the T3 lock, and the question's identity is checked again when the answer is back.

The launch carries everything the person said in the turn that asked, not the fragment that asked: the question is asked once, and its request is bound to the turn's final transcript.

When a launch names no project, the voice asks rather than states: with one project available it asks whether to start the thread there, and a yes starts it with the original request; with several it asks which one, naming them; with none it says so. Both questions are the ordinary pending ones, so a different project named in the answer, a no and an unrelated reply are read as they are for any launch confirmation.

## The relay wording, measured

A relay eval, an exploratory probe kept out of the repository, sends 22 call-shaped relays per wording through the GPU or CPU realtime build (two chat turns, a long hesitant request as audio, then the note) and scores each reply with the check the live turn uses. Measured on 2026-11-18, GPU, synthetic voice: the wording that shipped on voice/main said the draft's words and no others on 13 of 22 and, on a second run, 15 of 22 (run-to-run spread of 2); with four examples 20 of 22; with no examples 7 of 22; with one example 21 of 22. The failures of the old wording were the call's own: "The draft is: ...", a lead-in sentence, an appended closing line, and a reply that ignored the draft. The remaining failures of the shipped wording swap the draft's names for the person's request, which the exact-words check holds. A second pass sends 12 requests and counts ordinary replies that carry the relay's words: the old wording leaked an example line in 2 of 12, four examples in 2 of 12, one example in 0 of 12.

Those instructions were standing ones, in the call's persona, and a bare greeting was answered from them: with the example, the example line in 2 of 10 greetings; without it, a question about the note in 4 of 10 (GPU). The instructions now ride in each note, closed with "(Reply with only these words.)", and the persona says nothing about notes. In the note with no example, 17 of 22 relays recited and 0 of 10 greetings were answered with a relay's words (GPU); an example in the note took recitation to 2 of 22, because the voice said the example. With the closing cue, 20 of 22 recited and 0 of 10 greetings leaked, on the CPU build only. The one retry is there for the remaining two.

The checker needs what a thread-less act means. Launch acts carry no thread, and the decider's unsupported-claim question answered yes to "Should I start a new coding thread in Voice sandbox?" in 3 of 3 calls, so each such draft waited. The request is no longer a slot of `confirm_launch` and `launched` either: the writer copied its reader example's request instead of a 40-word hesitant one. An act with no thread now sends its meaning to the checker as `says` (voice/t3/verify.py).

## A lookup and T3 work in one turn

A person turn with a T3 line speaks nothing free about the person's words. What the caller hears about T3 work is the checked line, and the turn's lookups follow it as updates. On a turn that also has a lookup to speak about, the call's voice first answers the audio in text only (`answer_unheard`, `output_modalities: ["text"]`). That answer is never spoken, never sent to the client and never checked. It is model text in the session, and it is there because the voice refuses a relay that comes straight after unanswered audio. The relay follows, then the lookup's note and its spoken reply, after the turn waits for running lookups. A turn whose words answered a T3 question says only the T3 line, and so does a T3 turn with no lookup to speak about, since its relay recites without an answer first.

Why each piece is there (measured, 2026-11-19, GPU, synthetic voice):

- On the 2026-11-19 call, every T3 line whose first relay was refused or answered with the weather came on a turn that had also asked for a weather lookup (5 of 9 lines). The voice answers a turn's requests in the order they were asked, and refuses the one it has nothing for.
- A spoken reply to the audio before the relay fixed the relay but not the reply: on the mixed rehearsal it refused or claimed the thread ("I've started the thread on converting the audio presets", "I can't check the weather in Denver, but I can help you start the thread") on 9 of 10 mixed turns, and fifteen note wordings and a persona sentence did not end that on held-out turns.
- llama.cpp takes no assistant item (`server-realtime.cpp`, `on_item_create`: "only user messages and function call outputs are supported"; refused at runtime too), so the model has to write the answer.
- The text-only answer is usually a refusal or a claim about the thread. Spoken updates after it named no thread in 40 of 40 probe turns and 20 of 20 rehearsal turns. Capped at 4 tokens it no longer absorbs the audio: the spoken update then claimed the thread on 8 of 10 turns. A text-only answer to the lookup's note instead of the audio was repeated in the spoken update, claims included, in 3 of 10 probe turns.
- With the update before the relay, no later turn repeated it, but 4 of 7 unquoted thread confirmations ("Is X the thread you mean?") were answered "Yes, ..." instead of said, over three runs and both cue placements. With the relay first and the cue after the words, 5 of 5 were said.
- Moving "(Reply with only these words.)" before the words stopped the probe's voice reading it out (3 of 20 to 0 of 20), but the rehearsal's voice never had in 369 relay replies, and with the cue moved a relay-first run lost 1 of 2 unquoted confirmations to a "Yes, ...". The cue stays after the words.

The mixed rehearsal (`python -m voice.live.rehearse drive --mixed`: five calls of two chat turns, a weather lookup and a thread request in one breath, a yes, a weather lookup and a status question in one breath, and a yes; calls 1, 2 and 4 ask for the lookup first). ## A follow-up about the thread just discussed

After the voice has said something about a thread (its status, its start, a message sent to it, or news of it), a follow-up that does not name it ("Is it done yet?", "Tell it to also add tests.", "Stop it.") is a T3 request about that thread. Before this, such a turn never reached T3: the decider saw no thread in the call's earlier tasks, because only a lookup carries a call, so on the call's turn it read such a follow-up as chat that needs clarifying even while it picked `t3_ask`, and the voice answered freely. "I wanted an update on the thread from before" was worse: the intent rules took "I wanted" as a correction, so the decider was never asked and the voice said "What did you want instead?".

The decider still makes every choice; it is given what it lacked. `T3Tasks.spoken_about` is the thread the call last said something about, cleared when a call starts, and the turn adds it to the earlier tasks the decider sees as the newest one, a `t3_ask` about that thread (`with_thread` in voice/prototype/run.py). A turn worded as a correction that changes no value of the call's newest task is asked of the decider like a request (`turn_intent`); a correction that does change one ("I meant Saturday" after a Friday forecast) still amends that task.

A status asked again with nothing new in T3's record since the last one was said carries `since_last_asked`, and its line says so: "There's nothing new from Tidy the Save Slots since I last told you. It's still working." With only the one `thread_status` example, the writer worded all 4 such lines as that example's news, "is still working and reports its status" (measured, GPU), so the act gets an example of its own (`SAID_AGAIN_EXAMPLE`).

Measured on the hosted d1.2 decider, `python -m voice.t3.eval.record_followups`, one reading per case, replayed by voice/t3/test_followups.py. The seen set was looked at while the design was made; the held-out set was written before any run and changed nothing.

## Summaries

The summarizer uses the configured text model, and the decider picks the thread. The separate LFM3 writer drafts what the voice will say, unless `VOICE_RENDERER` hands that to the text model. A summary that fails, or meets a client cooling down after a failure, leaves the act without a `summary` slot, and the writer still drafts the line; one that hangs holds the line for up to `SUMMARY_TIMEOUT_S` (10 s).

A summary is written only when the voice is about to speak about a thread: an answer to a `t3_ask`, a `done`, or a `needs_you`. `Speech.fill` reads the thread through the seam. The status and the pending need come from code. The summarizer gets the last reply and writes a one-sentence gist into the act's `summary` slot. The thread's title is given as a name only, not as evidence of what was done. A thread with no last reply is summarized from its status and need. The gist is cached per thread, read sequence, and question. A speculative gist from words still being spoken serves only a final question with the same words. When the decider marks a `t3_ask` while Mason is still talking, `T3TaskService.sync` starts the read and the summary at once, and the answer after his yes reuses them.

The seam limits what a summary can see. The read carries no tool runs, changed files or errors, and it cuts the last reply at 1,200 characters (`apps/server/src/voiceSeam/outcome.ts`). Giving the summarizer more means changing the seam's read.

## Guarding it

`python voice/ci/check_spoken.py` fails on any string literal on the T3 speaking path that reads as speech, on an act built with wording in a slot, and on a string literal handed to a T3 speaking entry point anywhere under `voice/`, tests aside. Its tests plant each kind of line to show it is caught.

## What the check cannot see

The draft checks use the act as their source of facts. They do not read the original records behind a summary. A gist can overclaim ("it covered the tests" for a thread that was about to write them), and only the eval catches that. The decider's answers are noisy near its 0.5 line: the same request has drawn 0.51 and 0.67 on one question (measured). A borderline line can pass or fail on different calls. The reply check compares text, so it cannot detect a difference between the text and the generated audio.
