# Spoken acts: how the voice says T3 news

Nothing the voice says about T3 work is a hard-coded string (Mason, 2026-11-18). When he asks how a thread is going, he hears a short answer drawn from the thread's records, not the first two sentences of its last reply.

## The path

1. Code emits a typed act with the facts and evidence sequences from a T3 result, event, or read. For example, `confirm_tell` carries the thread title and the proposed message.
2. A separate text-only LFM3 realtime session drafts a short line. It gets instructions for the act kind, including an example that treats a thread title as the name of an existing conversation. Set `VOICE_RENDERER=particle-1` for the OpenRouter text model, `VOICE_PAID_TEXT_MODEL` to opt into a paid text model, or `VOICE_RENDERER=local` for a separate local chat server. [Local renderer probe](local-renderer.md) When that draft is refused by the checks, the text model behind the lane (the one writing summaries) words the acts once more, told what was refused, and its line goes through the same checks.
3. Code checks the draft's form and named values. It rejects known thread or project titles and titles from prompt examples unless the act supplies them. A confirmation must be a question, and a line about a pending need must describe the need without reading out a command, path, or code. Liquid d1.2 then answers yes-or-no questions about the act's meaning, status, and factual claims. Both checks must pass.
4. A private text item hands the draft to the call's existing audio session, which says it. The call receives instructions to say the item's words and nothing else when the session opens, with no announcement, lead-in or closing line of its own. Those instructions must be in place before the first audio turn, because the realtime server then locks them.
5. The live server holds the call's audio until the complete reply text is the draft's words: the same words, up to case, punctuation, markdown and contractions, with no person flip, so "I asked" is never "you asked". The draft already passed both checks, so the same words need no second decider call, and any other words are not the checked line. The turn stops the response at the first word that leaves the draft, so a reply that goes off the words leaves only its start in the session: llama.cpp keeps everything a response generated and has no event that removes an item (`server-realtime.cpp`: a cancel ends the response at the token it reached, and the dispatch accepts only session, audio-buffer, item-create, response-create and response-cancel events). What the build allows, then, is that the stopped start stays in the session, and the measured question is whether the next reply carries it on: in 12 forced cancels, none did (GPU). No note about the held reply is sent, because the one that told the model to set it aside was read as the newest text and answered. A reply that leaves the words is asked once more in the same turn with a new copying instruction before the quoted script (`MAX_RELAYS`). Both notes say that the caller's turn has already been handled. One that fails twice, has no audio, or is cut off goes back to be said when the call is quiet (`run_idle`), and a question goes back too, because nobody can answer a question they never heard. A question waits that way only while it is still the open one nobody has heard: once a turn asks it again, or a reply drops it, the waiting line is dropped with it (`T3Tasks.askable`). If the person starts talking while idle news is still being drafted, their turn can start without waiting for the draft. A confirmation that was never heard is asked again before a yes can authorize an action.

A yes authorizes one prompt. The question the voice asked belongs to the call it was asked in, and only a prompt whose audio was sent (`T3Tasks.spoke`) can be answered. The next person turn answers it or drops it: an unrelated reply, a turn that ends without answering, another line said after it, a hang-up, a reconnect and 90 s since it was heard (`CONFIRM_TTL_S`) all clear it, and a question is never asked a second time on the strength of a reply that answered nothing. A prompt the person never heard comes back to be asked again and acts on nothing. When a second prompt replaces the first, only the last one can be answered.

Picking the thread: the decider picks the thread a request means, and no chat model or word match does (`Decider.picks`, voice/t3/verify.py). One typed choice has the listed threads as its options, newest first and up to 40, each with its project and state, plus "not listed" (the words name or describe a thread that none of them is) and "unclear"; the thread the call last spoke about rides along, so "it" can mean that one. The answer's shares decide what happens. A thread with 0.9 or more is one the decider is sure of: a question about it is answered at once, with no "do you mean". A thread with 0.5 or more is confirmed back, unless the request is a question about the thread this call last spoke about: that one is answered at once, because an ask only reads and its answer names the thread. Otherwise the voice asks which, offering the threads that got 0.1 or more, or the three newest when none did. "Not listed" says there is no such thread. A message or a stop is always confirmed, however sure the pick. A question about a thread whose title another thread shares is confirmed too, and a message or a stop for such a title is not offered at all: the question could only name the title, so a yes could act on the wrong thread, and the voice says so (`same_title`). When the decider saw only part of the listing, "not listed" says how many threads were checked. No answer (no decider, a timeout) picks nothing and asks. On the recorded picks (`voice/t3/fixtures/thread_picks.json`, d1.2, 90 rows: 45 made-up requests over a listing of 12 and one of 40, 40 rows from requests written before any was run) 88 rows are placed as their case says, and no row is sure of a thread the request does not mean. The two misses are "and that one?" over each listing, which gives the thread last spoken about 0.50 (0.3 to 0.68 in earlier recordings); it is the only thread offered, so it is still confirmed. A pick is one decider call, a median of 121 ms and a p95 of 253 ms over the 90 recording calls (measured), off the T3 lock. The local d1-2B gives the thread it rightly picks a lower share than the hosted d1.2 does, so its client sets its own sure bar, 0.7 (`D1Client.pick_sure`), chosen on the same 90 rows: 70 are then placed as their case says, against 46 at 0.9, and no row is sure of a wrong thread (`voice/t3/fixtures/local_thread_picks.json`, measured). On the 40 rows of `voice/t3/eval/pick_holdout.py` the local d1-2B places 39 and the hosted d1.2 places 38, neither sure of a wrong thread (measured). Those 130 rows tuned the "not listed" wording: worded as "a thread that is not one of these", the local d1-2B called a vague "how is that one?" with nothing discussed not listed on 10 of its 16 such requests, and now on none; it seems to have read the option as "none of these" (inferred). On 32 more rows written before that and scored after (`voice/t3/eval/fresh_holdout.py`), the local d1-2B places 28 and d1.2 places 32, neither sure of a wrong thread and neither calling any of the 8 vague requests not listed (measured; an earlier wording was scored on them first, and the one change after was made for a regression d1.2 showed on the 130 rows). The local misses left are "it" with a thread just spoken about, which it mostly asks about rather than confirms, and descriptions by state ("the one that failed").

Reading the answer: the decider reads every reply to a T3 question (`Decider.reads`, voice/t3/verify.py), and no word list or pattern in code reads it. One typed choice asks what the reply does: yes, no, a question, another target, or nothing. It splits a bare "yeah?" between yes and question (0.48 and 0.33 on the hosted d1.2; "okay?" 0.36 and 0.45), because a transcript marks a rising voice with a question mark, so a yes is not read from it alone. Three yes-or-no questions beside it are asked in the same call. Does the reply say yes to what was asked (a bare yeah, sure or okay counts however it is said; a condition, a change or another target does not; neither does an unsure "maybe", an echo of the question, agreement with something else, or a word cut off)? Does it ask the assistant for information, an explanation or a different choice before deciding (a bare word of agreement is not asking, even with a rising voice)? Does it add a remark, a fact or an opinion about something other than what was asked? One function, `reads_yes`, combines them, and it is the only thing that can authorise an action. A reply is a yes only when every answer it rests on is present, well formed and in range, and all of these hold: the choice's own label is yes, or question (the marked yes); the choice's shares name all five labels and sum to one, and yes and question together are at least 0.5; a no and another target each have at most 0.2; the first question is at 0.5 or more, the second under 0.7 and the third under 0.5; and, when a launch question has other projects on offer, the target answer is present and says the proposal is kept at 0.6 or more. A missing or partial answer, a malformed or out-of-range number, a choice that says no, other or unrelated, and a target answer that is missing are each not a yes, whichever kind of confirmation is asked (`voice/t3/test_reads_yes.py` is the truth table, for each kind). A no cancels. A question or an unrelated reply answers nothing and the question is dropped. A no to "do you mean this thread", and only that question, carries a fourth question: does the reply take the whole request back ("never mind", "forget it"; "no, not that one" and "the other one" do not)? A no that does drops the question, says nothing about a thread, and lets the turn go on as talk; any other no to it looks for another thread. A no to a launch, a message, a stop, an approval, a denial or an answer is never read that way and cancels it. When a launch question has other projects it could mean, the same call carries a second choice: does the reply keep the proposed project, change to a named one, or change without making clear which. A named change, or a change with only one other project, asks a new confirmation for that project; a change with several asks which. A named project still goes through `pick_project` first. A question that lists choices ("which thread", "which project") sends the list in the order it was said and asks which one the reply chooses, so "the second one" answers by place and "the clamp one" by name. A reply to "which thread" that asks for a thread that was not listed is looked up among every thread, as a new reference; any other reply that chooses none drops the question, which is never asked twice. Threads that share a title cannot be told apart by voice, so the newest stands for the title, and one title left is confirmed, not listed. A reply the decider cannot read (no decider, a timeout, a score that is not a number from 0 to 1) answers nothing, so nothing acts. On the recorded replies (`voice/t3/fixtures/reply_reads.json`, d1.2, 102 rows) all 29 yes replies of launch, stop and tell questions act and none of the 54 other replies to them does. The made-up cases are in `voice/t3/eval/reply_marks.py` (recorded by `record_reply_marks`, replayed by `voice/t3/test_reply_marks.py`), two draws each except the last set. Compared with voice/main's rule on the same recorded answers (every recorded row of each kind, the fresh sets included), a real yes is taken more often for launch (66 of 73 against 52), stop (11 of 11 against 6), message (10 of 10 against 5) and thread (6 of 7 against 2), as often for approve (2 of 2) and answer (2 of 2), and not at all by either rule for deny (0 of 2: "yes, deny" and its cut-off form read as other or no). The replies that are not a yes and are taken are 5 of 150 for launch against 8, 1 of 6 for answer against 2, and none for approve, deny, stop, message and thread (1, 0, 2, 0 and 1 on voice/main). "Easier" is only for a reply the transcript marked as a question, and each of the guards above applies to it.

The launch carries everything the person said in the turn that asked, not the fragment that asked: the question is asked once, and its request is bound to the turn's final transcript. A dispatch that falls back to a lookup keeps the original tool choice. This lets the launch absorb a continuation that the decider read as starting the thread or sending it a message, even if the dispatch gate converted it to a lookup. A message that identifies an existing thread still gets its own answer.

When a launch names no project, the voice asks rather than states: with one project available it asks whether to start the thread there, and a yes starts it with the original request; with several it asks which one, naming them; with none it says so. Both questions are the ordinary pending ones, so a different project named in the answer, a no and an unrelated reply are read as they are for any launch confirmation.

## The relay wording, measured

A second pass sends 12 requests and counts ordinary replies that carry the relay's words: the old wording leaked an example line in 2 of 12, four examples in 2 of 12, one example in 0 of 12.

A question whose audio never reached the caller still needs to be asked before they can answer it.

### What can still end silent

A turn can still end in silence if the caller interrupts, every text writer is unavailable, the decider is unavailable, or the call cannot recite a checked acknowledgment.

## A thread still titled with the request it started from

A thread the voice starts is titled with the first line of what the person said, cut at 80 characters with an ellipsis, until T3 names it (`titleOf` in `apps/server/src/voiceSeam/launch.ts`, `launch_title` in `voice/t3/journal.py`). A spoken request is long and hesitant and has sentence breaks inside it, so that title is no name: the writer dropped the part after the first stop or "finished" a cut word, the slot check refused the draft for missing the title, and the form check counted the title's own stops and ellipsis against the line (the words were all there, spelled with "..." in place of the title's "…"). Two drafts failed, and the caller heard the `unanswered` fallback.

Changes, one per cause:

- **The form check masks a named value's own characters** (`acts.masked`): its words, in order, and the punctuation the value itself has, so a name said whole is not judged on its own stops or ellipsis. A character the value does not have, between its words or after them (a backtick, a `!`), stays for the form checks to judge.
- **An act about a launched thread that T3 has not yet named carries `begun_in` (its project) in place of `thread`**, and the line says "the thread you started in X". "You started" covers exactly the threads the voice launched on the person's request, in this call or an earlier one (the journal's `START` tasks); a thread another client made is the person's and is named by its title. The thread is picked by its id (`Update.thread_id`), never by title text, and its title is read from T3's listing when the line is worded (`speech.reference`, `T3Tasks._named`): a thread T3 has named since the act was made is worded with its current title, and two launches with the same request keep their own projects.
- **The project alone is used only when it tells the thread from the others the caller could mean**: no other launched thread in that project still carries its launch title. When there is one, the act also carries `begun_for`, what the thread was started for: a short noun phrase written from the request the person spoke and nothing else (`Speech.account`, `local_summary.account_messages`), passed by its own gate question against that request ("does `account` state something the request does not support?", bar 0.10), cached per request, and checked in the line like a summary (`a{n}_begun_for`). With no gated account (no gate, no answer, an account it doubts) the title stays: it is unsayable, but it does not name another thread, so a status line is not worded with a reference that could mean two threads and a confirmation never names an ambiguous one. Other threads of the project that the voice did not start do not make the reference ambiguous: they are not "the thread you started". Threads that share an identical title are left to the `same_title` guard.
- **A which-thread question offers each launched thread that T3 has not yet named by what it was started for** (`candidate_names`, `T3Tasks._offered`), and any other thread by its title; with no gated account it offers the titles, as before.
- **Refusals tell the writer what to change.** The generic "states something the facts do not support" refusal now says to say only what the act means, and `NO_THREAD` with `other` is told to the checker as what it means (no other thread besides the one turned down), where it only saw `other: true`.

## What a line says a pending request is about

A needs-you line, a status line for a thread waiting on a request, and a correction used to be given the request's stored text (`prompt`, `pending`) and told to say what it was about. A command line in `pending` was read out in a status line that passed its checks, and a made-up purpose passed the generic unsupported-claim question at its 0.5 bar (1 of 4 invented purposes in the eval; one scored 0.37).

The description of a request now comes from the approval path only ([live-reply-check.md](live-reply-check.md)): `Speech.fill` takes `prompt` and `pending` out of the act and puts `request` in their place. `request` is the description `Speech.describe` returns for the thread's request as the read holds it, and only when the stored text of the act is the stored text of that request. It is written from the request alone, passed by the approval gate, bound to the request's id and content, and never a summary. A tool permission, a file read, a missing detail, a refused description, no gate, or a gate that gives no answer leave `request` out, and the line says only what kind of thing the thread waits for. No summary is ever written from a pending request: the one place a summary is made (`Speech._summary`, which a prefetch, a cache hit and a reuse all pass through) gives the model the thread without its request, and a thread with only a request has nothing to summarise.

The line check asks about it (`voice/t3/verify.py`): with `request`, whether the line says what the description says, whether it says anything about what the request does or is for beyond it, and whether it reads out a command, program, file name or path; without it, whether it says what the request is for at all, apart from the thread's name. A description the writer cannot word without reading something out costs the line: the second draft of a line that carries `request` is worded without it (`speech.without_request`), with the refused wording left out of the request, because the writer copied it back (3 of 3 second drafts, with it in).

Invented labels and purposes about 6 made-up pending commands, each said as a faithful line, one naming another action (label) and one saying what the command is for (purpose), each checked once with a gated description and once with none (`line_eval`, hosted d1.2):

| Check                                                           | Faithful passed | Invented labels passed | Invented purposes passed |
| --------------------------------------------------------------- | --------------- | ---------------------- | ------------------------ |
| Base: the stored text in the act, generic unsupported question  | 6 of 6          | 1 of 6                 | 0 of 6                   |
| After, with a description (the line must carry it, add nothing) | 6 of 6          | 0 of 6                 | 0 of 6                   |
| After, no description (only the kind of request)                | 6 of 6          | 0 of 6                 | 0 of 6                   |

The same eval's earlier set of four invented purposes passed 1 of 4 on base. These are small sets written by one author, and the question's bar was not tuned.

A reading-out question on the description itself (is it a program or file name?) was tried at the gate and refused 7 of the 32 faithful descriptions of the approval cases that the gate passes (25 kept), which are mostly descriptions that say "file", so it was dropped; it would have cut the approvals that are confirmed by voice.

**Cost.** In the eval, 33 of 42 acts about a pending request carried a description, and 12 of 18 descriptions of the 6 made-up commands passed the gate in a timing run; a gate run's sandbox command never gets one, because the gate refuses its description (see [live-reply-check.md](live-reply-check.md)). The description takes the place of the summary these lines used to wait for, and it is quicker: the local 1.7B and its gate took a median 204 ms (p95 230 ms) to describe a request, against 273 ms (p95 298 ms) for the summary of the same thread, so nothing is added before the line is spoken (measured, 18 each, GPU). The extra is the second draft that drops the description when the first is refused, which is one more writer call on that turn.

## Corrections, approvals and withdrawn questions

[live-reply-check.md](live-reply-check.md) covers three more kinds of line: a free reply that claimed something about a thread is checked against T3 and corrected (a `correction` act); a pending permission request can be approved or denied by voice (acts `confirm_respond`, `responded`, `nothing_pending` and `needs_the_app`, and a `respond` seam operation), with the confirmation carrying a description of the request; and a question the caller never answered is told to the voice model once as withdrawn. The `same_title` line has an example shape that the voice recites (24 of 24 relays).

## A lookup and T3 work in one turn

A person turn with a T3 line speaks nothing free about the person's words. What the caller hears about T3 work is the checked line, and the turn's lookups follow it as updates. On a turn that also has a lookup to speak about, the call's voice first answers the audio in text only (`answer_unheard`, `output_modalities: ["text"]`). That answer is never spoken, never sent to the client and never checked. It is model text in the session, and it is there because the voice refuses a relay that comes straight after unanswered audio. The relay follows, then the lookup's note and its spoken reply, after the turn waits for running lookups. A turn whose words answered a T3 question says only the T3 line, and so does a T3 turn with no lookup to speak about, since its relay recites without an answer first.

## A follow-up about the thread just discussed

After the voice has said something about a thread (its status, its start, a message sent to it, or news of it), a follow-up that does not name it ("Is it done yet?", "Tell it to also add tests.", "Stop it.") is a T3 request about that thread. Before this, such a turn never reached T3: the decider saw no thread in the call's earlier tasks, because only a lookup carries a call, so on the call's turn it read such a follow-up as chat that needs clarifying even while it picked `t3_ask`, and the voice answered freely. "I wanted an update on the thread from before" was worse: the intent rules took "I wanted" as a correction, so the decider was never asked and the voice said "What did you want instead?".

The decider still makes every choice; it is given what it lacked. `T3Tasks.spoken_about` is the thread the call last said something about, cleared when a call starts, and the turn adds it to the earlier tasks the decider sees as the newest one, a `t3_ask` about that thread (`with_thread` in voice/prototype/run.py). A turn worded as a correction that changes no value of the call's newest task is asked of the decider like a request (`turn_intent`); a correction that does change one ("I meant Saturday" after a Friday forecast) still amends that task.

- A text item is appended to the open user turn. A note sent after the turn's audio is in the same user turn as the audio, which is the guide's mixed turn, not a turn of its own.
- A response with text and audio opens with `<|mixed_start|>`, the guide's prefill; a text-only one cannot switch to audio. An assistant item is refused, so the guide's few-shot turns cannot be given: that would take a change to `on_item_create`.
- Text is sampled greedily, which is what the GGUF asks for (`general.sampling.temp` 0, `top_k` 1). Audio codes are sampled with the projector's settings (temperature 1.0, top-k 128, repetition penalty 1.1 over 4096 frames), the guide's values. `--temp` does not reach them and no session field does. The audio seed is random per response and the sampled frames feed back into the context, so the same input gives different text on another run.

## Summaries

The summarizer uses the configured text model, and the decider picks the thread. The separate LFM3 writer drafts what the voice will say, unless `VOICE_RENDERER` hands that to the text model. A summary that fails, or meets a client cooling down after a failure, leaves the act without a `summary` slot, and the writer still drafts the line; one that hangs holds the line for up to `SUMMARY_TIMEOUT_S` (10 s).

A summary is written only when the voice is about to speak about a thread: an answer to a `t3_ask`, a `done`, or a `needs_you`. `Speech.fill` reads the thread through the seam. The status and the pending need come from code. The summarizer gets the last reply and writes a one-sentence gist into the act's `summary` slot. The thread's title is given as a name only, not as evidence of what was done. A thread with no last reply is summarized from its status and need. The gist is cached per thread, read sequence, and question. A speculative gist from words still being spoken serves only a final question with the same words. When the decider marks a `t3_ask` while Mason is still talking, `T3TaskService.sync` starts the read and the summary at once, and the answer after his yes reuses them.

The seam limits what a summary can see. The read carries no tool runs, changed files or errors, and it cuts the last reply at 1,200 characters (`apps/server/src/voiceSeam/outcome.ts`). Giving the summarizer more means changing the seam's read.

## Guarding it

`python voice/ci/check_spoken.py` fails on any string literal on the T3 speaking path that reads as speech, on an act built with wording in a slot, and on a string literal handed to a T3 speaking entry point anywhere under `voice/`, tests aside. Its tests plant each kind of line to show it is caught.

## What the check cannot see

The draft checks use the act as their source of facts. They do not read the original records behind a summary. A gist can overclaim ("it covered the tests" for a thread that was about to write them), and only the eval catches that. The decider's answers are noisy near its 0.5 line: the same request has drawn 0.51 and 0.67 on one question (measured). A borderline line can pass or fail on different calls. The reply check compares text, so it cannot detect a difference between the text and the generated audio.
